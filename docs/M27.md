# M27 — Parameter Sweep and Candidate Store

M27 expands a bounded Cartesian parameter grid over one sealed M24 specification, sends the resulting specifications to the M26 worker, and stores only the requested top candidates as immutable SQL evidence.

## Run a sweep

First seal a real specification as described in [M24.md](M24.md). Its registered instrument and candle range must exist in SQL Server. Then copy and adjust [../samples/parameter-grid.json](../samples/parameter-grid.json). Grid keys must already exist in the baseline specification.

```powershell
New-Item -ItemType Directory -Force ./artifacts | Out-Null
dotnet run --project src/Trading.Api -- sweep-parameters `
  --file ./artifacts/backtest-specification.sealed.json `
  --grid ./samples/parameter-grid.json `
  --worker vectorbt `
  --output ./artifacts/parameter-sweep.json
```

The planner rejects unknown parameters, duplicate values, duplicate JSON properties, more than 10,000 combinations, more than 100 stored candidates, invalid candidate specifications and existing output files. Parameter and grid ordering do not control candidate rank. Results are ordered by score and then specification hash.

`ParameterSweeps` stores the baseline, dataset, grid, worker request/evidence and final artifact identities. `BacktestCandidates` stores the exact sealed specification, parameters, exploratory metrics and status for each retained candidate. Unique indexes prevent the same worker/version/grid from being stored twice and prevent duplicate ranks or specifications within a sweep.

Apply migration `20260916061108_M28ResearchCandidates` with `database-update`, or run [sql/M28-Research-Candidates.sql](sql/M28-Research-Candidates.sql) in SSMS. `GET /api/parameter-sweeps` and `GET /api/parameter-sweeps/{id}` expose stored evidence.
