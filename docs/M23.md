# M23 — Risk-gated semi-live and direct live entry

M23 adds two production-data workflows for a single intraday long-option LIMIT entry:

- **semi-live** reads current Zerodha funds, positions, day orders and market depth, applies the complete evidence and M18 gates, persists a proposal, and sends no order;
- **direct live** performs the same checks and can submit that protected LIMIT buy to Zerodha only after the shared kill switch is released, two independent local opt-ins, `operatorApproved: true`, and an exact CLI confirmation.

The adapter follows Zerodha's official [quote](https://kite.trade/docs/connect/v3/market-quotes/), [funds](https://kite.trade/docs/connect/v3/user/), [positions](https://kite.trade/docs/connect/v3/portfolio/), and [order](https://kite.trade/docs/connect/v3/orders/) contracts. REST requests send `X-Kite-Version: 3` and `Authorization: token api_key:access_token`. Credentials stay in User Secrets and are never included in artifacts or logs.

## Apply the migration

```powershell
dotnet run --project src/Trading.Api -- database-update
```

This creates `dbo.LiveOrders`. Startup never changes schema. The SSMS alternative is [sql/M23-Risk-Gated-Live-Trading.sql](sql/M23-Risk-Gated-Live-Trading.sql).

## Gates applied to both modes

The command requires an unexpired, hash-valid M19 certificate and verifies every M22 paper artifact linked to it. Committed defaults require at least 10 paper sessions, 30 filled paper trades, and positive aggregate paper net P&L. These are eligibility minimums, not proof that live trading is safe or profitable.

The committed `LiveTrading:KillSwitchEngaged` value is `true`, so both modes fail closed. Release it only in local configuration when you intentionally want a semi-live proposal or direct submission:

```powershell
dotnet user-secrets set "LiveTrading:KillSwitchEngaged" "false" --project src/Trading.Api
```

Re-engage it after the session by setting the value back to `true`.

Immediately before proposal creation, M23 retrieves broker funds, net positions, today's orders and full quote depth. It fails closed unless:

- account and quote snapshots are no more than five seconds old;
- the account has positive available cash, no open net position, and no order activity today;
- the quote identity matches token, exchange and trading symbol and has valid bid/ask depth;
- the LIMIT buy is at least the current ask and no more than 25 basis points above it;
- stop is below limit, target is above limit, and M18 approves the whole-lot quantity;
- the M19 tested risk and maximum-lot limits are not exceeded.

The zero-day-order rule makes M23 a deliberately narrow first-live boundary: after any broker order activity, it refuses another entry because durable fill/exit reconciliation is not yet implemented. The broker checks are point-in-time REST reads rather than an atomic account lock, so do not place or modify orders in Kite concurrently while this command is running.

## Semi-live proposal

Update [../samples/live-entry.json](../samples/live-entry.json) with the current contract identity, unique request ID, current marketable limit, stop, target, lot size, and UTC entry/exit times. Semi-live does not require `operatorApproved: true` because it never submits.

```powershell
dotnet run --project src/Trading.Api -- live-order `
  --mode semi `
  --certificate-id 00000000-0000-0000-0000-000000000000 `
  --file .\samples\live-entry.json `
  --output .\artifacts\semi-live-proposal.json
```

The result records the certificate and paper-evidence hashes, account snapshot, quote, exact M18 decision hash, quantity, lots and guarded price. Place it manually in Kite only after reviewing the proposal and current account.

## Direct live submission

Direct mode is disabled in committed configuration. M38.1 additionally requires a matching, fresh M37 authorization; see [M38.1](M38.1.md). In addition to releasing the shared kill switch, enabling direct submission requires two separate local values:

```powershell
dotnet user-secrets set "LiveTrading:AllowDirectOrders" "true" --project src/Trading.Api
dotnet user-secrets set "Zerodha:AllowLiveOrders" "true" --project src/Trading.Api
```

Set `operatorApproved` to `true`, use a new request ID, and run:

```powershell
dotnet run --project src/Trading.Api -- live-order `
  --mode direct `
  --certificate-id 00000000-0000-0000-0000-000000000000 `
  --file .\samples\live-entry.json `
  --automation-authorization .\artifacts\controlled-automation-decision.json `
  --output .\artifacts\direct-live-order.json `
  --confirm PLACE-LIVE-ORDER
```

Before the network submission, M23 persists a unique `Prepared` record keyed by request ID. A successful response updates it to `Submitted` with the Zerodha order ID. If the response or persistence outcome is uncertain, the command returns exit code 4 and instructs you not to retry; reconcile the prepared request/tag in Zerodha first. A returned order ID means the OMS accepted the request, not that the exchange filled it, as Zerodha's order documentation explains.

`GET /api/live-orders` lists audit records and `GET /api/live-orders/{id}` returns the latest exact artifact. `/api/status` reports whether both direct-order gates are currently enabled without revealing credentials.

## Boundary before broader live trading

M23 submits BUY, LIMIT, MIS, DAY only. It does not claim fills, place stop/target exits, poll order history, handle partial fills, reconcile trades, permit a second order that day, recover a submitted position, or run unattended. Stop and target are risk evidence for review; they are not broker orders in M23. Those capabilities must be completed and tested before the direct route can be considered a complete live strategy lifecycle. Keep the kill switch engaged and both direct gates disabled until then.
