# M10 — Operational out-of-sample testing

M10 turns the M8 holdout engine and M9 report builder into one reproducible local command. It reads historical candles from the configured SQL database, freezes the current `vwap-ema-trend-breakout-v1` parameters, evaluates only later out-of-sample sessions and creates a new JSON evidence artifact.

## Run an OOS test

Run from the repository root. Replace the instrument ID and date range with registered data from the `Market` database.

```powershell
dotnet run --project src/Trading.Api -- run-oos `
  --instrument-id 00000000-0000-0000-0000-000000000000 `
  --timeframe 5 `
  --from 2025-01-01T00:00:00+05:30 `
  --to 2026-01-01T00:00:00+05:30 `
  --training-sessions 180 `
  --embargo-sessions 2 `
  --initial-capital 100000 `
  --allowed-risk 750 `
  --maximum-capital 100000 `
  --maximum-lots 2 `
  --slippage-bps 5 `
  --cost-profile zerodha-nse-equity-intraday-2026-03-01 `
  --output .\oos-nifty-2025.json
```

Optional `--strategy-id` accepts any ID in the M14 default catalog. When omitted, the command retains `vwap-ema-trend-breakout-v1` for backward compatibility.

`--from` is inclusive and `--to` is exclusive. Both values must contain `Z` or an explicit UTC offset. `--timeframe` uses the minute values defined by `Timeframe`: `1`, `3`, `5`, `15`, `30`, `60` or `1440`.

Required cost-profile values are:

- `zerodha-nse-equity-intraday-2026-03-01`
- `zerodha-nse-equity-options-2026-04-01`
- `none`, only when an intentionally frictionless control run is required

The options profile is valid only when the stored candles contain actual option premiums. Applying options costs to Nifty or Sensex underlying prices does not create an option backtest.

## Deterministic workflow

1. Validate every CLI option before querying SQL.
2. Confirm that the instrument exists and obtain its stored lot size.
3. Page the half-open candle range in blocks of 10,000 without dropping the boundary candle.
4. Use the first `training-sessions` as historical context, followed by the optional embargo.
5. Construct the already declared strategy with its default frozen parameters. M10 does not optimize against training or test results.
6. Evaluate candidates only inside the remaining OOS sessions.
7. Apply risk-based whole-lot sizing, adverse slippage and the selected dated cost model.
8. Build the M9 report from test candles only.
9. Write the complete artifact atomically to a new `.json` path.

The command refuses to overwrite an existing report. Choose a new filename for every run so evidence from a prior experiment cannot be silently replaced.

## Artifact contents

The schema-versioned artifact records:

- test type and selected strategy ID;
- instrument, timeframe and exact training/test session boundary;
- source, training and testing candle counts;
- all M7 performance metrics and daily OOS equity;
- M9 R, duration, exit, monthly, yearly, weekday and time-bucket sections.

The command prints only a compact completion summary to stdout. Detailed evidence stays in the JSON output file.

## Exit codes

| Code | Meaning |
| ---: | --- |
| `0` | OOS report created |
| `2` | Invalid arguments, unavailable data or output-file problem |
| `3` | Database or unexpected processing failure |
| `130` | User cancellation |

## Boundaries

M10 is a single final chronological holdout using a predeclared strategy. Reusing the same OOS period to modify parameters contaminates that holdout. The command does not persist or index reports in SQL, add them to the `/api/reports` catalog, select option contracts, rank strategies or authorize orders.

M10 adds no database table, migration, package, Azure resource, AI call, broker connection or live execution path.

## Validation

```powershell
dotnet build TradingCommandCenter.sln --no-restore
dotnet test TradingCommandCenter.sln --no-build
```

Fixtures verify SQL-backed OOS execution, artifact boundaries, JSON creation, no-overwrite behavior, explicit time zones, required risk inputs and invalid request rejection.
